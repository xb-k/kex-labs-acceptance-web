# 收敛调度 (Convergence Orchestration)

> 目标：**一次做对**。把「好几轮才到需求」压成「判据先行 → 一轮开发 → 一轮验收」。
> 实测病根（近 3 天会话）：一个目标最多派 **51** 个子任务；6 轮验收往返；34 个微任务。

---

# 0. 何时用

- Slow Path 目标预计要派 ≥2 个子 Agent（改代码 / 修 bug / 调性能 / 重构）。
- 看到「dev → 验收 FAIL → dev 修 → 再验收」的循环苗头。
- 一个目标已派 ≥3 个子任务还没收敛 → **立即停下，回本 SOP 重排**。
- ⚠️ **纯文档 / 配置 / 文案类（L0）不用本 SOP** —— 见下节分级。

---

# 0.6 闸〇 · 环境先行（跑任何全量套件之前）
按顺序跑这 5 条，**异常先处理再跑套件**：
1. `docker ps --format '{{.Names}} {{.Status}}'` —— 看 Qdrant/DB/Redis 的 **up 天数**（实测：Qdrant up 11 天后在集合建删风暴下返回 `500 channel closed`/404/409 ⇒ 白烧 2 轮）。
2. `curl -s -o /dev/null -w '%{http_code}' localhost:6333/healthz` —— 期望 200。
3. `pgrep -fl uvicorn` —— 看有没有**孤儿实例**（实测有 pid 跑在 `:8079`）。
4. `docker run --rm --privileged alpine df -h /` —— Docker VM 磁盘（满了会让 Qdrant 建集合失败 `No space left on device`）。
5. `uptime` + `nproc` —— load 常态 40+，别在满载时并发重活。
可执行脚本：`~/.config/opencode/scripts/check_test_env.sh`（只读检查，输出 5 行结论）。

# 0.5 工作分级与派发目标（先分级，再决定走几步）

**不是所有工作都要「判据先行 + 验收」。给非代码工作套测试是纯空耗 —— 用户明确反感「写个文档也测试」。**

| 级别 | 典型工作 | 流程 | 派发目标 |
|---|---|---|---|
| **L0 轻量** | 写文档 / README / 说明、改配置、一行文案、跑条命令 | **只走 ② 一步**；不冻结判据、不派验收、**不要求「测试通过」**；写完自己读一遍即可 | `dev`（纯探查用 `explore`） |
| **L1 标准** | 单模块代码、普通 bug、加一个函数 | ② + dev 交前自测；**不单独派验收** | `dev` |
| **L2 重工程** | 跨层链路 / 性能 / 事故 / 数据口径 / 多文件重构 | ① → ② → ③ 全流程 | 诊断/修复 `dev`；冻结判据 + 验收 `acceptance-tester` |

**判级口诀**：改的是**代码逻辑**吗？不是（文档/配置/文案）→ **L0**。是，但只碰一个模块 → **L1**。跨层 / 性能 / 事故 / 口径 → **L2**。

## 派发目标选择（**先判域，再判性质；禁止无脑派 dev**）

→ **单一真相源**：agent 分类学 + 域注册表 + 路由规则见 `~/.config/opencode/references/agent-taxonomy.md`（**不在此处重复**）。

# 1. 标准流程（把「N 轮」压成「3 步」）

```
① 判据先行 (acceptance-tester · 用例先行，只读，可与②并行)
       ↓ 产出 acceptance/<id>/{spec,testcases}.md（冻结）
② 一轮开发 (dev · 单工单，工单内带 ①的 acceptance_criteria)
       ↓ 交前自检：dev 自跑 ①的用例，附逐条结果
③ 一轮验收 (acceptance-tester · 对着 ①的冻结用例判 PASS/FAIL/BLOCKED)
       ↓
   FAIL=0 ──→ 放行（非阻塞项进 POLISH.md，不再开轮）
   FAIL>0 ──→    仅把 FAIL 项合并成「一个」修复工单，回到 ②（最多 2 次）
```

> 各阶段的**产物与出口判据**（规格 / 计划 / 实现 / 验收 / 排障 / 交付 / 文档）见 skill `dev-cookbook`（Master 与子 Agent 共用同一本）。

# 2. 五闸细则

## 闸一 · 合并 (Batching)

- 一个**目标** = 一个 dev 工单。工单里的 `instruction` 用编号列表写清全部改动点。
- **禁止**把「改一行 / 搬一个文件 / 补一处注释 / 复核一次」拆成独立子任务。
  判据：如果一条改动**不需要新的验收轮**、也不需要独立证据，它就该并进上一条工单。
- 反例（实测）：`T-285 搬T284证据到可读路径`、`T-299 修detect_env注释裸路径` —— 一行改动占一整轮。

**批次 ≠ 目标**（本机实测教训，2026-09-30）：一个**批次** = 一组相关的 `app/**` 改动。
- **全量 `pytest` + `behave` 只在「批次出口」跑一次**（出口 = 准备换线发货前）。
- 批内迭代只跑**相关子集**：`pytest <相关文件>` / 单条 feature / 定向断言 —— 不许每件都付一轮全量。
- 一次全量 ≈ **28 分钟**（本机实测：pytest ~12min + behave ~15min）⇒ 同批 3 件共用一轮，省 ~1 小时。
- **例外（不许省）**：触及**检索排序 / 两个地板 / 加密 / 迁移 / 数据口径**的改动，其「相关子集」必须含该域的**全族**用例（那两个地板是逐字红线）。
- 报回时必须**区分**「相关子集绿」与「全量绿」，**不许把子集绿说成全量绿**。

## 闸二 · 判据先行 (Criteria-First)

1. 先派 `acceptance-tester`（prompt 里写明「**用例先行模式**：只读文档，不执行、不起服务、不碰代码树」）。
2. 产出 `acceptance/<id>/spec.md`（可观测断言）+ `testcases.md`（冻结用例）。
3. 把冻结判据**原样**抄进 dev 工单的 `acceptance_criteria`。
4. **判据含糊 = 此时就报**：例如「≤60s」必须定义成「滞后上界 = 同步周期 + 轮耗时」这类可判口径；
   否则 dev 与验收各按各的理解做，必然多一轮（实测 T-031 就卡在这）。
5. **L0 / L1 跳过闸二**（见 §0.5 分级）：纯文档 / 配置 / 文案 / 一行改动**不派验收、不冻结判据**；
   L1 只在工单里写死可观测断言让 dev 自测即可。
6. **成本提示（防惯性全面冻结）**：一份冻结判据 ≈ **3–5 分钟**子 agent 时间 + 一条后续要维护的用例链。⇒ **只为 L2 冻结**；**L0/L1 不冻结**（L1 把可观测断言写进工单让 dev 自测，见 §0.5）。UI / 展示 / 单模块 = **L1**。
7. **冻结产物按「最小可判集」**：够判就停，**不追求用例数量**；抽检档 ≤20 条。

### 闸二附则 · 白盒审查（条件触发，**不新增轮次**）

> 验收是**黑盒**（判行为对不对）；它天然抓不到「改了共享方法语义、别处没跟」这类**静默漏改**（实测 DISCO `调整超限`：6 个调用点全丢返回值 → 静默放行）。补一道**白盒**审查。

- **触发**：L2 **且**改动触及「共享方法 / 公共 API / 返回或异常语义 / 契约文件 / 数据口径」→ 派 `reviewer`（三轴：规范 / 需求 / **影响面·契约**）。
- **不触发**：L0/L1、纯 UI 展示、纯文档。**别全审** —— 全审 = 撞多轮。
- **并列**：与 ④验收**并行**（两个独立读者，互不污染），**绝不串行加轮**。
- **出口**：发现分 `blocking` / `non-blocking`；`blocking` 并入修复单（回 ②，≤2 次口径同验收），`non-blocking` 进 `POLISH.md`。
- **反模式**：把 `reviewer` 当第二个验收关串在验收**之后**（= 多一轮）；或对每单都派（= 防多轮的反面）。

## 闸三 · 根因优先 (Root-Cause-First)

- 适用于：性能回退、线上事故、反复复现的疑难 bug。
- **先派一个只读诊断工单**：只查不改，产出「按置信度排序的根因清单 + 每条的证据（文件:行 / 数据）」。
- **仅「不可复现 + 误判会致生产事故」才升三阶**（缺一不可）：按 `references/master/progressive-delivery.md` 走「观测 → 影子 → 切流」；上一阶数据不达标，**不得派下一阶**。影子必须无副作用，切流必须有回滚开关与守护指标。
- 可复现 bug 走红→绿；影响面小的最多只做观测（O），不强制影子 / 切流；L0 / L1 不适用。**禁止把三阶扩大化**。
- 再由**一个**合并修复工单覆盖全部根因。
- **禁止**按症状逐个派（反例：首屏慢拆成 `T-027 懒加载` / `T-028 物化库` / `T-030 版本链` 三轮，其实该先诊断出根因再一把修）。

## 闸四 · 收尾止损 (Stop-Loss)

- 验收 **FAIL=0** 之后：
  - **只有阻塞级**发现（数据 / 口径 / 交互正确性 / 白屏 / 回归）才允许再开轮；
  - 非阻塞的「顺带发现 / 体验项」→ 追加到 `<项目>/POLISH.md`，**合并成至多 1 轮**收尾，不许逐条派。
- 反例（实测）：`T-035` 已 10/10 PASS 并写明「可放行」，Master 仍把 4 条非阻塞项做成 `T-036`，再派 `T-037` 复验 —— 白烧两轮。
- **出口判据**：FAIL=0 且无阻塞项 ⇒ 直接报「可放行」，放行权归人。

## 闸四附则 · 防过度收敛 (Over-Convergence Defense)

> 闸一「合并」与闸三「根因连带关闭」都很激进 —— 但它们**默认"同类即可连坐"**，一旦误关就**永久丢失**。
> 本附则是那两闸的**安全网**：目标不是少收敛，而是**误关可自愈**。

- **收紧判据**：只对「**共享根因 + 症状同类**」才合并 / 连带；**局部、症状不同类的一律不连坐**。
- **可逆标记**：被「根因连带关闭」的项，出口时打 **`待复核` 标记 + 根因引用 + 说明**，**不写终态**（不是「已解决」，是「暂缓」）。
- **复核债 + 自动重开**：靠**周期性重扫 / 回归**兜底 —— 问题仍在 ⇒ **自动重新打开**该票，不靠人记得回来捞。
- 判据：任何一次「连带关闭」如果**说不出共享根因**，就不许连带（回到闸一逐项处理）。

## 闸五 · 禁轮询 (No Polling Tickets)

- 等待异步结果（构建 / 长任务 / 外部服务）**只许**靠：系统事件回传、读落盘看板（`TASK.md` / `SUBAGENT_STATUS.md`）。
  （Master 的 `subagent_watch` 已在配置里关停，**不要**再指望主动轮询。）
- **严禁**派 dev 去「探查构建是否在推进 / 再探进度 / 检查任务状态」。这类轮询工单一个都不许有。
- 反例（实测）：`探查backend构建是否在推进`、`再探v7任务确切进度`、`检查任务执行状态和卡死子任务`（34 个子任务）。

# 2.5 测试栈窗口互斥（共享资源）
- 本仓库 `features/steps/migration_steps.py:19` 把 `_LEGACY_COLLECTION` **写死 `test_ltm_semantic`** ⇒ **`pytest` 与 `behave` 绝不能并发**（互抢同一集合，双双变红）；**别人的残留**也会让 `test_live_store_has_no_stray_collections` 假红。
- ⇒ **同一时刻只允许 1 个任务使用测试栈**（`pytest`/`behave`）。**真正要串行的不是"写代码"，是"测试栈窗口"** —— 只读探查、UI 静态改动、文档改动可以并行。
- 🔴 **发代码单之前必须确认在跑的验收单的套件已经退出**。「看板显示某任务正在跑」**不等于**「它不会马上跑套件」（实测：发了代码单，验收单的 `behave` 正好启动 ⇒ 白烧一轮 + 一条 BLOCKED）。

# 3. 目标级熔断

- 同一目标连续 **≥3 轮**未收敛，或子任务数 **≥5**：
  **停下**，向用户报三件事 —— ① 为什么不收敛 ② 卡在哪 ③ 建议怎么切（换选型 / 缩范围 / 人工介入）。
- 绝不无限追打。宁可交一个诚实的「未收敛 + 卡点」，也不要烧掉几十轮。

# 4. 反模式清单（出现即违规）

| 反模式 | 症状 | 纠正 |
|---|---|---|
| 微任务化 | 一行改动一个子任务 | 并进同一工单（闸一） |
| 判据后置 | dev 做完才由验收定标准 | 用例先行（闸二） |
| 跳过影响面审查 | 改了共享方法语义没核调用点（静默漏改） | 条件触发 `reviewer`（闸二附则，与验收并行） |
| 症状派单 | 同一根因拆成多轮修 | 先诊断后一把修（闸三） |
| 追打非阻塞 | FAIL=0 后还为体验项开轮 | 进 POLISH.md 合并收尾（闸四） |
| 轮询工单 | 派 dev 去「看进度」 | 用事件/看板（闸五） |
| 无限收敛 | 目标派到几十个子任务 | 目标级熔断（第 3 节） |
