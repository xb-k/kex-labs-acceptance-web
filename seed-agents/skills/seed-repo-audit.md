# repo-audit：仓库瘦身与过度设计审查

一句话：**先证明它真的没人用，再谈删；每一条发现都必须给得出触发场景。**

## 铁律

1. **只读审计，不改代码**。本技能只产出清单，落地改动交 `dev`（且要单独派单、单独验证）。
2. **判定「未使用」前必须全库 grep**，包括 `tests/`、`fixtures/`、脚本、配置、模板、动态引用
   （字符串拼接的 import / `require(` 变量 / 反射式注册 / 插件目录扫描）。只搜 `src/` 就下结论 = 不合格。
3. **每条发现必须给具体触发场景**：谁会在什么情况下用到它 / 为什么确认没人用。**没有场景不算发现**，
   不要用「看起来没用」「可能不需要」凑数。
4. **按优先级排序**，可删行数多的、风险低的排前面。删不动的（公共 API / 外部契约）单列并说明风险。
5. **不要顺手改别的**：审计中发现的功能 bug 记进清单末尾，不动手。

## 检查清单

| 维度 | 找什么 |
|---|---|
| **删除** | 死代码（无调用点）、未引用的 export、永远走不到的分支、注释掉的旧实现、多余的 wrapper |
| **复用** | 重复 helper / 组件 / 格式化逻辑 / 几乎一样的两个函数；该用仓库已有实现却重写了一遍 |
| **原生替换** | 标准库或平台 API 能做的却引了依赖（`left-pad` 式）、自造 `debounce`/`deepClone`/日期格式化 |
| **合并** | 只被调用一次的过细文件 / 抽象层（拆成 30 行一个文件但只有一个调用方） |
| **YAGNI** | 单实现接口、单产品工厂、纯转发 wrapper（参数原样传给下层）、预留但没人用的配置项 / 扩展点 |

## 前置证据要求（每条发现都要带）

- **全库引用搜索结果**：`rg -n "<符号>" .`（含 tests / fixtures / 脚本），贴命中数；0 命中才可判「未使用」。
- **动态引用排除**：字符串拼出来的路径、`require`/`import` 变量、插件目录自动扫描、模板里的名字 —— 说明你查过。
- **可替代实现的位置**：若判定「应复用 / 应删」，指出仓库里已有的那个实现（`文件:行`）。
- **预估可删行数**：用 `wc -l` 或 diff 估算，给出数字区间，不要写「若干行」。

## 输出格式

```markdown
## Refactor List（按优先级）

### P1｜可删 <N> 行｜风险：低
- `src/lib/foo.ts:12-88` —— 死代码：`formatLegacyDate` 全库 0 引用（见证据）；替换方案：直接删。
  - 触发场景：<何时会用到 / 为什么确认没人用>
  - 证据：`rg -n "formatLegacyDate" .` → 0 hit（含 tests/fixtures）

### P2｜可删 <N> 行｜风险：中
- ...

### P3｜仅记录，不建议动
- ...

## 未审阅的部分
- <目录/文件/原因：太大 / 生成代码 / 无权限 / 未覆盖的动态引用>
```

**最后一行必须是「未审阅的部分」** —— 没扫到的范围要写清楚，不许用「全部已审」蒙过去。

## 交付前自检（提交改动前 30 秒过一遍，防「顺手加」）

只问三句，答不上来就别加（展开见 `agent/dev.md` §「最小完整改动」①–⑤）：

1. **这层抽象有第二个调用方吗？** 只有一个 → 不进抽象，写在调用处。
2. **这个配置项 / 参数现在有人改吗？** 没人改 → 不预留，等真需求来了再加。
3. **这行依赖能用已装的或标准库替掉吗？** 能 → 不新增依赖；能改 5 行 → 不新建文件/类。

命中「该加」的，本 skill 不算例外：**先写清触发场景**（谁会在什么情况下用到），再落地。

## 反模式

- ❌ 只看 `src/` 就判「未引用」（漏 tests / fixtures / 动态引用）
- ❌ 拿「代码风格旧」「看起来复杂」当删除理由
- ❌ 把「可以引入某某库/框架重写」当瘦身建议（那不是删，是加）
- ❌ 边审计边改代码（审计与改动混在一轮，等于没证据）
- ❌ 输出一张没有行数、没有路径、没有证据的「建议清单」
