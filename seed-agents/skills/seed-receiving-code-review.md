# 接收代码评审 (Receiving Code Review)

> **触发**：你（`dev` / 域 agent）收到 `reviewer` 的三轴 findings，或用户 / 上游给的评审意见。
> **一句话**：**评审意见是输入，不是判决。** 逐条处理 —— 别整批吞，也别整批顶。

## 0. 先分清谁在发、发了什么

- 发方 `reviewer` → 每条带 `axis`(规范 / 需求 / **影响面·契约**) + `severity`(blocking / non-blocking) + `文件:行` + 依据。**按条处理**。
- 发方 `acceptance-tester` → 那是 **FAIL / BLOCKED**，走验收修复口径（不套本 skill）。
- 发方用户 → 同样逐条；对「规范 / 口径」分歧先看 §3。

## 1. 逐条三步：核实 → 分类 → 动作

对**每一条** finding：

1. **核实**：自己去看那条 `文件:行` / 调用点 / 依据，**独立复核**（不因为对方说了就信）。
2. **分类**（三选一，必须落一条）：
   - **接受**：确实是问题 → 修。
   - **反驳**：误报 / 不成立 → **带反证**（`文件:行` / 复现命令 / 引用规范原句 + 为什么这里不适用）。
   - **待澄清**：意见含糊、缺上下文、说不清对错 → **问**（`input_required`），别猜着改。
3. **动作**：接受 → 修 + 在回报里给**对照原发现**的证据；反驳 → 写清为什么；待澄清 → 挂起并注明。

## 2. 铁律

1. **不无脑照单全收** —— 按误报把好代码改坏，就是新 bug。误报要带证据顶回去。
2. **不无脑顶回** —— 反驳必须有证据；「我觉得没问题」不算。`blocking` 级**无证据反驳**的，就必须修。
3. **每条要能追溯** —— 接受 / 反驳都要落到**规范 / AC / 调用点**；「因为评审说了」不是理由。
4. **不含糊带过** —— 说不清就 `input_required` 问，别默默跳过、也别猜着改。
5. **不借机扩大范围** —— 只处理 findings 指向的问题；顺带发现按 `dev.md` §七 报告，**不动手**。
6. **blocking 先闭环** —— 先处理全部 `blocking`（修或带证据驳回），`non-blocking` 进 `POLISH.md` / 标记待办。

## 3. 分歧怎么判（规范 / 口径类）

- 依据是**仓库的单一真相源**（`AGENTS.md` / `CLAUDE.md` / 契约 / AC），不是谁嗓门大。
- 评审引用的规范**过时 / 不适用本场景** → 反驳，并把「规范该更新」记进报告（别只改代码、不动规范）。
- 真拿不准且影响大 → 交 Master / 问用户，**别自行放宽阈值**。

## 4. 回报格式（逐条，短）

每条 finding：

```
finding# → 结论(接受|反驳|待澄清) → 证据(file:line / 复现 / 规范原文) → 动作(改了啥 / 为啥不改)
```

> 配套：发起侧 = agent `reviewer` + skill `code-review`；调度层 = skill `convergence-orchestration` 闸二附则。
