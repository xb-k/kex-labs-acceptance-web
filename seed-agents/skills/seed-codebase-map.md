# codebase-map：先画地图，再动手

一句话：**每条结论都要能落到 `文件:行`；落不到的写成「未确认」，不许猜。**
（借 Graphify 的关系图谱与 Understand-Anything 的架构理解：先把结构定下来，再改代码。）

## 何时做 / 何时不做

- **做**：陌生仓库；改动跨 ≥2 个模块；跨层链路；要评估影响面（谁会被我这一改带崩）。
- **不做**：单文件 ≤5 行改动；纯文档 / 配置 / 文案（L0）；项目已有 `<项目>/docs/codebase-map.md`（**读它，只补变化**）。
- **只读**：本步骤不写产品代码；发现 bug 记进地图「高风险区」，不动手。

## 五段式（缺一段 = 没做完）

| # | 段 | 要回答 | 证据要求 |
|---|---|---|---|
| 1 | **模块边界** | 有哪几块、各自职责、谁依赖谁 | 每块给入口文件 + 主目录；依赖给「A → B」并在代码里指出调用点 |
| 2 | **入口** | 请求/命令/事件从哪进来 | 路由注册、CLI 入口、页面挂载、定时任务、消息监听的 `文件:行` |
| 3 | **数据流** | 一条主链路怎么走、在哪变形 | 3–5 跳调用链，每跳 `文件:行`；写清序列化/事务/缓存边界 |
| 4 | **扩展点** | 要加功能该改哪儿 | 注册表 / 插件目录 / 配置加载 / 抽象基类的 `文件:行`；**没有就写「无扩展点，需改 X」** |
| 5 | **高风险区** | 碰了容易出事的地方 | 并发/锁、事务边界、金额与精度、鉴权、外部调用与超时、兼容性契约；给 `文件:行` |

## 采集手法（只读，命令合批）

1. `cat AGENTS.md` / `CLAUDE.md` / README → `git log --oneline -10` → `ls` → 技术栈文件（`package.json` / `pyproject.toml` / `go.mod`）+ 测试怎么跑。
2. 入口：`rg -n "app\.(get|post)|router|@click|if __name__|main\(|addEventListener"`（按技术栈换成真实写法）。
3. 数据流：从**一个真实入口**往下跟 3–5 跳，别把整个仓库都读一遍。
4. 扩展点：`rg -n "register|plugin|entry_points|registry|load_config"`，命中后**打开文件确认**是不是真的注册表。
5. 高风险区：`rg -n "transaction|BEGIN|lock|mutex|Decimal|float\(|password|token|timeout"`。

## 输出

- 落到 `<项目>/docs/codebase-map.md`（已有则追加一节并标日期，**不另建编号碎片文件**）。
- 结构就是上面五段；开头 3 行写清「这份地图覆盖什么 / 覆盖到哪个 commit」。
- 篇幅 ≤120 行，只写能核对的事实；不抄 README 宣传语，不写「应该 / 可能 / 大概」。
- 需要画关系时用 **Mermaid**：**每张图必须有标题与图例**，节点名用真实文件/函数名（不要 F1/A/B 之类占位）。
- 项目 `AGENTS.md` 禁止新增文档 → 不落盘，地图正文直接回传工单。

## 反模式

- **只看目录名推断职责** —— 必须打开入口文件确认。
- **把「常见分层」套上去凑五段** —— 该仓库没有 service 层就别编。
- **地图里全是类名、没有 `文件:行`** —— 无法核对 = 没做。
- **边画边改代码** —— 画完（或工单确认）再进实现阶段。
